# Codex 桌面端：从本地项目到 GitHub PR

## 目标

帮助用户在 Codex 桌面软件中完成一次可追踪的开发任务：选择正确的本地仓库，使用独立工作树，明确文件保存位置，向 Codex 下达充分清楚的任务，审查代码与测试，再通过 GitHub 分支和 Pull Request 交付。

优先根据用户**实际看到的界面**给出下一步操作；版本不同、菜单名称变化时，按功能解释，不把某个界面布局当成永久事实。一次只引导到下一处关键决策点。

## 1. 识别四种不同的对象

| 对象 | 含义 | 示例 |
| --- | --- | --- |
| Codex 项目 | 桌面软件里用于归类任务、关联源文件夹的项目 | `J2CJ-skills` |
| 源文件夹 | 真实 Git 仓库的本地根目录 | `D:\EDU\J2CJ` |
| Worktree 根目录 | 用于存放独立 Git 工作树的父文件夹 | `D:\Codex-worktrees` |
| 任务工作树 | Codex 为某次任务创建的独立检出目录 | `D:\Codex-worktrees\<自动生成的目录>` |

工作树根目录不是要添加到 Codex 项目里的“源文件夹”。创建父目录不等于已经创建 Git 工作树。开启“新建工作树”后，Codex 通常在选定的工作树位置创建具体任务目录。

## 2. 设置本地项目

1. 打开 Codex 桌面软件，进入或新建项目。
2. 在“编辑项目 / 源文件夹”里添加**代码仓库根目录**，例如 `D:\EDU\J2CJ`。
3. 用户原本已添加该仓库时，保留现有配置即可；无需再添加 Worktree 根目录。
4. 新建会话，确认运行位置是“此计算机 / Local”，而不是远程云端环境，特别是任务需要本机 SDK、编译器或私有实验数据时。
5. 若仓库含 `AGENTS.md`，引导 Codex 从中了解仓库约定、现状和已有工具。

## 3. 选择 Git 分支与工作树

在新任务的本地环境菜单中检查：

- **新建工作树**：当用户希望保留原有工作区、同时启动独立开发任务时开启。
- **分支**：选择本次开发要基于的分支。新功能通常从最新的 `main` 开始；如果项目有其他开发基线，以实际工作流程为准。
- **环境**：界面显示“无环境”时，通常表示没有额外选定的环境配置；这不等于无法运行本机工具。

如果界面当前显示 `research/...` 等历史实验分支，而本次任务应当基于主分支，应主动提醒用户切换。创建任务前核对本地 `main` 和 `origin/main` 的同步情况；更新仓库时先查看未提交改动，避免覆盖现有工作。

**Worktree 的作用**：不同任务可在不同目录中修改代码，同时共享 Git 历史。工作树的新文件**不会自动写回原始源文件夹**；应通过提交、分支、合并或变更移交把成果带回主项目。

## 4. 空间不足时的磁盘安排（Windows）

用户希望主要在 D 盘开发时，可以采用：

```text
D:\
├── EDU\J2CJ\               # 原始 Git 仓库（示例）
└── Codex-worktrees\         # 独立工作树的存放目录（示例）
    └── <任务工作树>\
```

引导用户在 Codex 设置中寻找 **Worktree 存储位置 / Worktree root** 一类的选项，并设置为期望的 D 盘目录；具体名称和可配置程度以当前软件版本为准。返回任务界面后开启“新建工作树”，并在任务实际启动时检查**真实工作路径**，确认它是否在 D 盘。

向 Codex 任务描述中注明：源码、下载资料、构建输出和可配置的临时数据优先放在 D 盘。提醒用户：软件配置、系统临时文件、用户配置目录、部分编译缓存仍可能占用 C 盘；**把工作树放在 D 盘不能保证 C 盘写入量为零**。如果 C 盘空间极低，结合实际工具进一步检查缓存和临时目录。

## 5. 构造开发任务提示词

为用户提供可直接粘贴到 Codex 的自然语言任务，而不预设不必要的技术实现细节。提示词通常包含：

1. **目标和交付物**：明确希望得到实际代码、一个 Skill、测试还是文档。
2. **项目上下文**：代码仓库位置、相关语言与工具链、入口文档和已有实现。
3. **需要解决的问题**：描述真实问题、现有现象、期望能力。
4. **参考材料**：相关开源项目、仓库文件、日志或测试案例。
5. **实施与验证**：明确希望 Codex 实现、运行测试、展示真实结果。
6. **磁盘和运行环境**：指定本地执行，以及大文件优先使用的磁盘。
7. **GitHub 交付**：要求在开发分支提交、推送、创建以 `main` 为目标的 Pull Request，并给出链接；用户审核后再合并。

可复用模板：

```text
请在当前本地仓库中完成 [任务目标]，交付可实际使用的 [成果]。

项目背景：[语言、工具链、现状、问题]。
请先阅读仓库的 [入口文档及关键路径]，研究并复用已有代码。
参考资料：[链接或文件]。

希望实现的核心能力：[具体能力与使用场景]。
请自主设计合适的实现方式，完成代码、必要测试和使用说明。

本地源仓库：[路径]。
工作树存储位置：[路径]。
生成的大文件和可配置缓存优先放在 [磁盘]，并核实实际工作目录。

完成后请在独立开发分支提交、推送到 [GitHub 仓库]，
创建面向 main 的 Pull Request，提供 PR 链接、变更摘要、测试结果和使用方法。
```

## 6. Codex 开始运行后的协作

- Codex 请求权限时，根据它准备执行的命令或访问的资源帮助用户判断。
- 如果 Codex 先写了一份方案，用户要求的是实际开发，就提醒它继续实现、测试并交付代码。
- 若 Codex 报告无法访问 SDK、依赖或源码，检查任务工作树与原始仓库的区别：未跟踪或被 `.gitignore` 排除的本地文件不会因为创建工作树而自动出现。
- 对于长任务，优先通过当前 Diff、日志与测试结果检查真实进展，而不是只依赖自然语言的“完成”陈述。

## 7. 验收和 GitHub 同步

开发结束后，协助用户完成以下检查：

1. **文件**：列出实际创建和修改的文件，查看关键 Diff。
2. **功能**：能否真实安装、启动或调用所要求的产物。
3. **验证**：列出运行过的测试、执行结果，以及尚未验证的环节。
4. **存储**：确认新工作树和主要生成文件的实际路径。
5. **Git**：确认开发分支、commit、remote、push 状态。
6. **PR**：确认 PR 链接、目标分支 `main`、变更摘要、测试信息。
7. **审查与合并**：如果用户要先审查，就先提供文件或 PR 供审查，确认后再合并。
8. **后续同步**：原本的本地仓库、其他设备或 Reasonix 不会因 PR 创建而自动更新；PR 合并后在对应工作区检查 Git 状态，再按项目规则同步 `main`。

成功交付的标准不是“Codex 已回复完成”，而是用户能够找到代码、看到验证证据，并明确知道成果位于哪个工作树、Git 分支和 PR。

## 8. 从今天的 J2CJ 案例理解流程

本例中的对象与选择为：

| 步骤 | 当时选择 | 原因 |
| --- | --- | --- |
| Codex 项目 | `J2CJ-skills` | 任务组织名称，不是磁盘目录 |
| 源文件夹 | `D:\EDU\J2CJ` | J2CJ 本地 Git 仓库 |
| 运行位置 | `此计算机` | 使用本地 J2CJ、Cangjie SDK 等环境 |
| 新建工作树 | 开启 | 与 Reasonix 原有工作区隔离 |
| 基础分支 | `main` | 从主分支上的现有研究成果开始 |
| 环境 | `无环境` | 暂不添加额外环境配置 |
| Worktree 根目录 | `D:\Codex-worktrees` | 希望主要任务文件放在 D 盘 |
| 开发任务 | `j2cj-repair` Skill V0.1 | 针对 J2CJ 转换后仓颉产物的适配修复 |
| 交付方式 | 开发分支 → GitHub PR → 人工审查 → 合并 | 方便跨机器及 Reasonix 同步 |

这是一次**操作指导示例**，并不表示 `j2cj-repair` 已经开发、测试、推送或合并。使用此 Skill 时，应根据用户当前项目替换这些路径和名称。

## 9. 遇到问题时优先排查

- **找不到源代码**：Codex 项目里添加的是仓库根目录吗？选中的工作树是否基于正确分支？
- **工作树没出现在 D 盘**：是否仅创建了 `D:\Codex-worktrees` 文件夹，却没配置软件实际使用的存储位置？检查真实工作目录。
- **看不到新文件**：文件可能位于任务工作树，而不是原始仓库。查看工作树路径或 Git 分支。
- **编译器或 SDK 不可用**：检查本机路径、环境变量、工作树缺少的忽略文件与工具链设置。
- **无法推送 GitHub**：检查仓库远程地址、权限与认证；区分本地提交成功和远程推送成功。
- **PR 创建后原仓库没更新**：PR 尚未合并，或本地原仓库尚未同步。
- **截图与说明不一样**：以用户截图中的真实控件为准，寻找功能相同的入口，再给出下一步。
